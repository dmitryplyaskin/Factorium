# Генерация блупринтов Factorium: исследование и предлагаемая архитектура

Исследовано 29 октября 2026 года. Это проект архитектуры, а не реализация генератора.
Изучены исходники и документация ниже; чужие тесты и бенчмарки не запускались.
Численный пример рассчитан по нашему `data/game/catalog.json` из Factorio 2.1.24.

Предлагаю строить компилятор фабрики: запрос пользователя → баланс производства →
производственные блоки с контрактами портов → размещение → маршрутизация → независимая
проверка → испытание в игре → экспорт. LP/MILP полезны для баланса и дискретного выбора;
эвристики и локальный SAT — для геометрии. Проверку нужно отделить от генератора.

### Quick-Blueprint

В `blueprint/blueprint.lua` собирается базовая ячейка: машина, подвод ингредиентов,
отвод продуктов, манипуляторы, трубы и столбы. Затем ячейка повторяется в линию.
Положение жидкостных портов учитывает ориентацию и размеры машины. Это полезный
пример генерации маленького блока, параметры которого получены из прототипов.
[Код генератора](https://github.com/Latias-m/Quick-Blueprint/blob/abd268aa28b0a42ada874c0bb9c87cd6ad3e687c/blueprint/blueprint.lua).

Число машин оценивается по времени рецепта, скорости машины, эффектам скорости модулей
и выбранной доле ленты. Расчёт использует максимальное потребление одного твёрдого
ингредиента и сумму количества твёрдых продуктов. В этой функции нет общего баланса
сопродуктов, продуктивности, вероятностных выходов и пропускной способности каждого
манипулятора. Это ограниченная оценка линии, которую нельзя использовать как общий
решатель цепочки. [Расчёт](https://github.com/Latias-m/Quick-Blueprint/blob/abd268aa28b0a42ada874c0bb9c87cd6ad3e687c/recipe/recipe.lua).

Для Factorium интересна идея параметризуемых ячеек, а также различие между начальным
`recipe.enabled` и доступностью рецепта у конкретной игровой силы. Полную архитектуру
планировщика этот проект не заменяет.

### Spaghettio

Это самый близкий аналог нашего пользовательского сценария. Важное расхождение:
README описывает рекурсивный обход, но актуальные `solver.rs` и `netflow.rs` уже
используют LP баланса потоков. Переменная рецепта одна на все его продукты;
побочные продукты учитываются в общем балансе. Из прежних проблем авторы выделяют
двойной подсчёт нефтепереработки, игнорирование сопродуктов и некорректный перевод
циклической потребности во внешний импорт.
[Текущий решатель](https://github.com/storkme/spaghettio/blob/cfe4a77615d458722869264350475b156cb56ffe/crates/core/src/netflow.rs),
[объяснение перехода на LP](https://github.com/storkme/spaghettio/blob/cfe4a77615d458722869264350475b156cb56ffe/docs/rfc-solver-net-flow.md).

Размещение строится вокруг рядов машин и общей шины. Для сложных пересечений есть
локальный SAT; для трассировки — A* и рост цены перегруженных участков. Отдельный
вариант соединяет готовые ячейки, а непосредственная передача между соседними
машинами выступает самостоятельной оптимизацией внутри обычной раскладки.
[Сравнение архитектур](https://github.com/storkme/spaghettio/blob/cfe4a77615d458722869264350475b156cb56ffe/docs/cell-vs-bus-architecture.md),
[локальный SAT](https://github.com/storkme/spaghettio/blob/cfe4a77615d458722869264350475b156cb56ffe/docs/junction-sat-and-caching.md).

Особенно полезен сам принцип ограничения решателя возможностями генератора.
`SolverError` явно различает неподдерживаемые циклы и конфигурации самовозврата.
Наличие корректного LP-решения не означает, что маршрутизатор умеет его построить.
В проекте есть также собственная модель динамики и испытания в настоящей игре;
документация отмечает расхождения производительности разных вариантов раскладки.
[Граница поддерживаемых циклов](https://github.com/storkme/spaghettio/blob/cfe4a77615d458722869264350475b156cb56ffe/crates/core/src/solver.rs),
[проверка в игре](https://github.com/storkme/spaghettio/blob/cfe4a77615d458722869264350475b156cb56ffe/docs/headless-verification-discovery.md).

Для Factorium стоит взять разделение баланса и геометрии, планирование общих потоков,
локальные решатели пересечений и проверку фактической доставки. Собственный симулятор
имеет смысл вводить позднее, если испытания в Factorio станут узким местом разработки.

### factorio-dsl-compiler

Основная сильная сторона — независимый `verify.py`. Проверяющий модуль восстанавливает
физические связи по размещённым сущностям, вместо доверия обещанию генератора о наличии
ребра графа. Проверяются геометрия, доставка, смешивание предметов и жидкостей,
электроснабжение. Генераторы v1/v2/v3 взаимозаменяемы.
[Проверяющий модуль](https://github.com/MrTsepa/factorio-dsl-compiler/blob/1e73fa940eb45337abcdf7fac9d573134b4366ea/fgr/verify.py).

В v3 маршрут объединяет нескольких потребителей одного потока в сеть. Поиск может
выбирать доступные стороны машин; конфликтующие сети повторно прокладываются с
растущими штрафами за перегрузку. Маршруты сначала существуют как планы, и только
потом превращаются в сущности. Это предотвращает рассинхронизацию карты занятости
с экспортируемым блупринтом. Бюджет поиска конечный; возврат лучшего состояния при
его исчерпании не является доказательством корректности — состояние всё равно
должен принять проверяющий модуль.
[Реализация v3](https://github.com/MrTsepa/factorio-dsl-compiler/blob/1e73fa940eb45337abcdf7fac9d573134b4366ea/fgr/layout_v3.py).

Есть важная оговорка: общий генератор v3 и генератор рядов машин для задач с целевой
скоростью решают разные задачи. В документации авторы сообщают, что в одном тесте
зелёных схем на 15/с общая раскладка имела 12 086 сущностей и оставалась в переходном
режиме, а вариант рядами — 613 сущностей и 14,43/с в установившемся режиме. Это
результаты авторов для конкретного случая, а не наш бенчмарк. Даже второй результат
ниже 15/с: связность и компактность сами по себе недостаточны.
[Расчёт скоростей, ряды и измерения](https://github.com/MrTsepa/factorio-dsl-compiler/blob/1e73fa940eb45337abcdf7fac9d573134b4366ea/docs/RATES.md).

Решатель скорости обходит уже заданный граф, размножает машины и входные порты,
учитывает калибровку манипуляторов. Для нашего автоматического выбора рецептов,
циклов и сопродуктов нужен дополнительный глобальный решатель.
[Код расчёта](https://github.com/MrTsepa/factorio-dsl-compiler/blob/1e73fa940eb45337abcdf7fac9d573134b4366ea/fgr/solver.py).

## Контракт пользовательского запроса

Основной интерфейс может остаться простым: продукт, единицы в секунду, готовые входы.
Остальные параметры задаются профилем по умолчанию с возможностью раскрыть настройки.

Нужно явно определить:

- Цель означает выпуск **не ниже заданного** в установившемся режиме при оговорённых
  входах, питании и свободном выходе. Ровно заданная скорость — отдельный режим с
  ограничением подачи или управлением. Округление количества машин даёт запас мощности.
- Выбранный готовый вход по умолчанию означает `import_only`: внутреннее производство
  этого ресурса отключается. `prefer_import` — другой режим, позволяющий дополнить
  ограниченную поставку внутренним производством. Политику для случайных сопродуктов
  таких ресурсов нужно определить отдельно.
- Допустимые базовые входы задаются профилем. Нельзя автоматически импортировать
  любой промежуточный продукт, который решатель не сумел произвести.
- Для входа можно задать верхний предел скорости; без предела решатель сообщает
  необходимое снабжение. Порт описывает предмет/качество, скорость, ленты, стороны
  лент, направление и координаты подключения.
- Планета, доступные машины, качество машин, качество ингредиентов, модули, маяки
  и исследования являются частью запроса. Версия игры, набор модов и startup-настройки
  должны совпадать с профилем проверки.
- Утилизация/экспорт сопродуктов, энергия и топливо явно входят в контракт. В первой
  версии разумно получать электричество извне; добычу руды и месторождения оставить
  за границей чертежа.

## Баланс производства: LP и MILP

Представим процесс `p` как фиксированный вариант:
`рецепт + машина + качество машины + качество рецепта + набор модулей + режим маяков`.
Не все комбинации разрешены; фильтрация по категориям, жидкостным портам, поверхности,
топливу и доступным технологиям происходит до оптимизации.

Для ресурса `i` и процесса `p`:

\[
S_{ip}=b_{ip}-a_{ip},\qquad
\sum_p S_{ip}x_p+u_i=d_i+v_i.
\]

`a` — расход на крафт, `b` — средний выход с учётом разрешённой продуктивности,
`x` — крафты/с, `u` — внешний ввод, `d` — требуемый внешний выпуск,
`v` — отдельно обслуживаемый избыток. Для запрещённых входов `u_i=0`.
Одна колонка процесса одновременно участвует в балансах всех сопродуктов.
Коэффициент одного ресурса, встречающегося с обеих сторон, сначала вычисляется как
единая разность. Две переменные для одной нефтепереработки по разным продуктам неверны.

`v` нельзя считать волшебным исчезновением. Положительный избыток должен получить
экспортный порт с достаточной скоростью, разрешённую цепочку переработки или другую
реальную утилизацию. Конечный сундук/бак не обеспечивает стационарный вывод.

Количество машин — целочисленное:

\[
0\le x_p\le \mu_p n_p,\qquad n_p\in\mathbb Z_{\ge0},
\quad \mu_p=\frac{\text{effective crafting speed}_p}{\text{recipe time}_p}.
\]

При фиксированной конфигурации это MILP. В первом приближении можно решить LP,
округлить машины вверх и проверить физическую реализацию. Для выбора между
несколькими типами машин и схемами кормления лучше оптимизировать дискретные варианты.
Продуктивность применяется к разрешённой части выхода, а не ко всему выходу вместе
с возвращаемым катализатором. Клиппинг эффектов и ограничения модулей вычисляются
до построения колонки; неизвестные множители нельзя просто перемножать с `x`
внутри линейной модели.

Порядок предпочтений должен задаваться профилем: экономия сырья, стоимость строительства,
площадь и энергия могут конфликтовать. Жёсткие требования к скорости отделяются
от стоимости. Для строгих приоритетов лучше последовательные оптимизации с фиксацией
достигнутого уровня, чем неподтверждённая иерархия очень маленьких `epsilon`.
Нужны допуски численной проверки и повторный расчёт невязок по исходным коэффициентам.

Результат решателя — не только числа машин. Нужны граф потоков с величинами,
использованные рецепты, потребление внешних ресурсов, избытки и объяснение отказа.
Исчерпание времени поиска отличается от доказанной несовместности запроса.

## Производственные блоки и размещение

Рабочая единица геометрии — проверенный блок из нескольких машин, манипуляторов,
локальных лент, труб и зарезервированных мест питания. Его контракт содержит
габариты, ориентации, порты, скорости по каждой стороне ленты, ограничения соседства
и условия, при которых проверена производительность.

Шаблоны должны описывать форму интерфейса: два твёрдых входа, три входа,
твёрдые входы плюс жидкость, несколько жидкостей, несколько выходов. Отдельный
шаблон на каждый рецепт не нужен. Неподдерживаемые размеры или расположения портов
должны отклоняться явно. Автоматический синтез нового микрошаблона через SAT/CP-SAT
можно добавить позднее и кэшировать результат после проверки в игре.

Большой выпуск делится на несколько блоков/рядов до размещения, исходя из пределов
транспорта. Простое увеличение длины одного ряда не решает перегрузку шины.
Несколько независимых копий всей цепочки — хороший запасной вариант, но округление
машин может сделать его дороже совместного производства; варианты нужно сравнивать.

Для начального размещения достаточно слоёв зависимостей, упорядочивания блоков для
уменьшения пересечений и зарезервированных коридоров. Полезная функция качества:

\[
J_{place}=\alpha A+\beta\sum_e f_eL_e+\gamma C+\delta P.
\]

`A` — площадь, `f_e` — поток, `L_e` — длина связи, `C` — оценка перегруженности
коридоров, `P` — неудобство внешних портов. Такая функция помогает расположить
часто передаваемые промежуточные продукты рядом. Прямая передача манипуляторами
выступает кандидатом, например для проводов и микросхем, и принимается только
при совместимых пропорциях и достаточной скорости.

Места питания нужно резервировать до маршрутизации, а реальную сеть столбов можно
достроить после неё. Итоговая проверка требует покрытия потребителей и связи столбов
с внешним вводом питания. Просто близость к любому столбу недостаточна.

## Ленты: геометрия и пропускная способность

Поток — сеть с несколькими потребителями, а не набор независимо проложенных
парных путей. Общий ствол допустим только при достаточной суммарной мощности.
Полосы моделируются отдельно, но остаются сторонами одной физической ленты:
нельзя независимо уложить две несовместимые геометрии на одном тайле.

Для каждого участка и стороны:

\[
\sum_i f_{i,e,\ell}\le c_{e,\ell}.
\]

Нужны также сохранение потока, допустимость предметов, направления подачи,
переходы полос на поворотах и боковых загрузках, фильтры и приоритеты сплиттеров.
Произвольное дробное распределение потока из LP не обязательно реализуется
конкретным сплиттером. Проверка сетевой ёмкости — необходимый фильтр, а не полная
замена динамической проверке.

Для манипулятора скорость зависит от источника/приёмника, геометрии, исследования
вместимости, качества, размера пачки и состояния ленты. Одного выражения через
скорость вращения недостаточно. Начальная стратегия — небольшая таблица измеренных
режимов, привязанная к версии игры и конфигурации. Новые режимы проверяются в движке.

Маршрутизация: A* с состоянием направления и ограничения выхода из тоннеля,
затем перепрокладка конфликтующих сетей. Цена тайла зависит от длины, поворота,
текущей перегрузки и истории конфликтов. Это позволяет первой сети уступить место
следующей. Подземные ленты требуют проверки фактического спаривания концов;
геометрическое пересечение тоннелей само по себе не означает конфликт.
Локальный SAT используется для небольших плотных узлов и балансировщиков.
[Пример предметной SAT-модели](https://github.com/R-O-C-K-E-T/Factorio-SAT).

Если коридор перегружен, обратная связь должна расширить его, разделить ряд,
изменить размещение или оборудование. Неудача одного эвристического маршрута
не доказывает, что рецепт вообще нельзя построить.

## Жидкости, циклы и случайные результаты

Жидкости — отдельные сети с типом, температурой, направлениями портов, фильтрами,
насосами, буферами и ограничениями протяжённости. Нельзя свести их к условию
«трубы соседствуют». Смешивание температур требует отдельного баланса тепла;
в первой версии лучше поддержать ограниченные проверенные температурные режимы.

Особенно важно совпадение версии: FFF-442 описывает изменение базового расхода через
соединение — от константы версии 2.0 к зависимости от объёма буфера — и новые
возможности выбора полосы выгрузки. Поэтому правила и калибровку из проектов для
2.0 нельзя без проверки переносить на нашу 2.1.24.
[Описание изменений разработчиками игры](https://updater.factorio.com/blog/post/fff-442).

После выбора активных процессов строятся сильно связные компоненты графа.
Для циклов стационарный баланс не доказывает возможность запуска: нужен стартовый
катализатор, физический возврат, приоритет рециркуляции и защита от тупиков.
Простые поддержанные циклы получают специальные блоки и стартовую ведомость;
остальные должны возвращать понятную ошибку. Переработку нельзя включать без
обслуживания её случайных сопродуктов и остатков.

Среднего выхода достаточно для первоначального баланса, но не для обещания
бесперебойной работы на конечном промежутке. В Factorio 2.1 нужно сохранять
`independent_probability` и `shared_probability`: общая случайная величина
коррелирует выходы. Для ответственных случайных цепочек нужен отдельный режим
планирования с буферами, горизонтом и уровнем риска, например:

\[
\Pr[Q_T\ge dT]\ge 1-\varepsilon.
\]

Это будущий контракт, не свойство обычного LP. Его нельзя подтвердить одним
коротким прогоном или повторением одного и того же детерминированного состояния.
Порча и качественная переработка также требуют времени пребывания и нескольких
классов ресурсов, а не одной усреднённой переменной на имя предмета.

## Пример по нашему каталогу: 2 красные микросхемы/с

Условия: обычные assembling-machine-2, скорость 0,75, без модулей и бонусов;
зелёные микросхемы, пластик и медные пластины поставляются извне.

| Величина | Расчёт | Результат |
| --- | --- | --- |
| Машины красных схем | `ceil(2 / (0.75 / 6))` | 16 |
| Требование проводов | `2 × 4` | 8/с |
| Выход одной машины проводов | `0.75 / 0.5 × 2` | 3/с |
| Машины проводов | `ceil(8 / 3)` | 3 |
| Внешние зелёные схемы | `2 × 2` | 4/с |
| Внешний пластик | `2 × 2` | 4/с |
| Внешние медные пластины | `8 / 2` | 4/с |

Это нижняя оценка числа машин по производству, а не проверенный физический чертёж.
Третья машина проводов должна работать частично; её запас мощности — не новый спрос
цепочки. При этом транспорт и подача должны выдерживать фактический режим работы.

Жёлтая лента в этом профиле переносит 15 предметов/с, одна сторона — 7,5/с.
Если все 8 проводов/с собираются только на одной стороне, выпуск красных схем
ограничен сверху `7.5 / 4 = 1.875/с` ещё до учёта манипуляторов. Нужно задействовать
обе стороны, разделить поток или применить прямую передачу. Именно этот разрыв
между расчётом машин и физической доставкой должна закрывать архитектура.

## Независимая проверка и испытание в игре

Проверяющий модуль получает конечные сущности/блупринт и контракт запроса. Он сам
восстанавливает физические связи, в том числе полосы и пары подземных лент, и
проверяет рецепты, коллизии, границы портов, жидкости, питание и необходимые ёмкости.
Нельзя считать список рёбер, записанный генератором, доказательством связности.

Испытание в Factorio должно импортировать именно экспортированную строку,
построить сущности, установить модули и рецепты, подать ресурсы через заявленные
порты с заявленными ограничениями и вывести продукты. Тестовые бесконечные источники
и приёмники находятся за границей пользовательского чертежа. Внутренних телепортаций,
неограниченных загрузчиков и дополнительного питания вне контракта быть не должно.

Измерять нужно чистый выпуск через внешнюю границу. Внутренняя статистика производства
не заменяет это измерение: циклы могут многократно учитывать один материал.
Ведомость стартового заполнения отделяется от постоянных входов. Нельзя незаметно
наполнить все буферы перед тестом и принять временную работу за устойчивый режим.

Нужны прогрев, несколько окон измерения, проверка тренда буферов и вывод причин
простоя: нехватка ингредиента, забитый выход, питание, топливо, жидкость и т.д.
Кандидат на 15/с, измеренный как 14,43/с, не должен автоматически получать статус
«цель выполнена». Точность измерения и допустимая погрешность задаются явно.
Результат испытания — подтверждение при конкретных условиях и горизонте, а не
доказательство поведения для любых модов и любого будущего состояния.

## Где уместна более сложная оптимизация

Практичный вариант развития — декомпозиция: мастер выбирает процессы, блоки и
их мощности; подзадача размещает и соединяет их. Доказанное ограничение разреза
сети даёт обратное условие на мастер, например суммарный поток через коридор не
может превосходить ёмкость отведённых полос. Обычный провал A* такого доказательства
не даёт; в этом случае применяются расширение, новые кандидаты или локальный поиск.

Далее полезны большой локальный поиск с разрушением/восстановлением проблемных
регионов, CP-SAT размещение прямоугольных блоков, выбор вариантов блоков по MILP,
оценка альтернатив с учётом целочисленного округления и маршрутов, а не только сырья.
Общая модель «каждый тайл всей фабрики — переменная» годится как исследовательский
режим или решатель маленького блока, но слишком тяжела как первый основной путь.

Прямое академическое подтверждение полезности декомпозиции есть в
[Towards Automatic Design of Factorio Blueprints](https://arxiv.org/html/2310.01505):
авторы разделяют выбор производства, упаковку и маршрутизацию после трудностей
единой модели. Их упрощения — один продукт у рецепта, отсутствие жидкостей,
одна полоса и идеализированные буферы — не позволяют считать эту работу готовой
моделью современной Factorio, но структура решения полезна.

## Предлагаемая последовательность реализации

1. `Request → ProductionPlan`: LP баланса, строгие внешние входы, совместимость машин,
   целочисленные количества, граф потоков, понятные ошибки. Результат доступен в JSON
   до появления раскладки. Первые проверки — сопродукты, общие промежуточные ресурсы,
   внешний ввод зелёных схем, недоступный рецепт и недостаточная поставка.
2. `ProductionPlan → BlockPlan → Layout`: повторяемые ряды без жидкостей, нормальное
   качество, без модулей и маяков, несколько полос и рядов при превышении ёмкости.
   Электричество подаётся извне. Независимый проверяющий модуль вводится вместе с
   первым генератором, а не после появления большого количества эвристик.
3. Экспорт строки и испытание в игре. Критерий — целевой внешний выпуск, а не только
   успешный импорт. Сохранение профиля, seed/параметров и отчёта для воспроизведения.
4. Жидкости и сопродукты с явными выходами; затем модули, продуктивность и прямые
   передачи; затем поддержанные циклы, порча, качества и более плотные раскладки.

На Rust стартовый LP можно сделать через [microlp](https://docs.rs/microlp/latest/microlp/):
он написан на Rust и работает в WASM. Для более тяжёлых MILP стоит сравнить его с
[HiGHS](https://highs.dev/) на нашем корпусе задач, сохранив интерфейс backend.
Для локальных булевых ограничений подходит [Varisat](https://github.com/jix/varisat).
[CP-SAT](https://developers.google.com/optimization/cp/cp_solver/) полезен для
целочисленной геометрии; его ограничения требуют целых коэффициентов, что нужно
учесть при масштабировании дробных величин.

Ближайшая конкретная задача для Factorium — решатель производственного плана с
контрактом входов. Он даст проверяемую основу для геометрии и не потребует сразу
решать общую задачу оптимального размещения всех сущностей игры.
